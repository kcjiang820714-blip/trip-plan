# 一筆預訂多張個人票券設計規格

## 目標

讓一筆交通或票券類預訂保存共同資訊一次，並可在同一筆預訂內新增多張個人票券；每張票券各自選擇持有人與提供方式。

## 資料模型

既有 booking 的共同欄位維持不變：名稱、日期時間、地點、交通資訊、訂位代碼、備註。

新增 `booking.personalTickets` 陣列：

| 欄位 | 用途 |
| --- | --- |
| `id` | 個人票券 ID |
| `holderUserId` | 指定旅伴的使用者 ID，可空白 |
| `holderName` | 指定時的顯示名稱 |
| `ticketUrl` | 電子票券網址，可空白 |
| `attachments` | 此人專屬的圖片／PDF 附件陣列 |

每一張個人票券可使用網址或附件；同一筆預訂可建立任意多張票券，但每張票券只屬於一位持有人。

## 舊資料遷移

- 保留既有 `booking.ticketHolderUserId`、`ticketHolderName`、`ticketUrl`、`attachments` 的讀取相容。
- 若 `personalTickets` 不存在但舊 ticket URL 或附件存在，正規化時建立一張隱含的個人票券，持有人取既有欄位。
- 沒有舊票券的 booking，`personalTickets` 為空陣列。
- 新版儲存只寫 `personalTickets`；舊單張票券欄位在記憶體保留為空，避免同一檔案被重複顯示。

## 表單行為

僅在交通、景點票券、活動類預訂顯示「個人票券」區塊；餐廳與住宿維持既有訂單附件欄位。

- 建立者可按「新增一張個人票券」。
- 每張票券列包含：持有人、提供方式（連結／上傳檔案）、網址欄位或檔案選擇、移除按鈕。
- 持有人下拉列出建立者與已受邀旅伴，並可選「尚未指定」。
- 可在同一次儲存建立多張票券；共同預訂資料只填一次。
- 附件需在儲存前逐張讀取、驗證與上傳，並沿用圖片／PDF 限制。

## 顯示與篩選

- 建立者：看到共同預訂及所有個人票券，並可看到每張持有人。
- 旅伴：看到共同預訂資訊，但只看到自己持有的個人票券與「出示票券」按鈕。
- 其他旅伴的票券網址、附件、檔案名稱與持有人資訊不渲染到該旅伴的票券區塊。
- 今日快速取用將同一預訂中，目前登入者的個人票券各自顯示為可出示項目；建立者看到全部。
- 未指定票券只顯示給建立者。

## 範圍與限制

- 沿用目前信任旅伴的介面篩選，並非嚴格資料隔離。
- 不改 Supabase 資料表、Storage bucket 或 RLS。
- 不改共用交通路線、班次、時間與持有人之外的既有預訂行為。

## 驗證標準

- 建立者可建立一筆交通預訂，並在同一表單中為三位旅伴新增三張不同票券。
- 旅伴 A 只看到 A 的票券；旅伴 B 只看到 B 的票券；建立者看到三張。
- 三張票券可混用網址與圖片／PDF 附件。
- 共同預訂資訊只出現一份，且只填寫一次。
- 舊單張票券資料升級後仍可由原持有人與建立者開啟。
- 餐廳與住宿的既有附件流程不受影響。
