# Supabase 登入同步閘門設計

## 目的

已登入 Supabase 的使用者進入 app，或手動登入成功後，必須先完成該帳號的 Supabase 同步，才可查看或操作旅程。這個閘門避免短暫顯示上一位使用者或舊本機快取的旅程，也避免並行同步互相覆寫畫面。

同步畫面固定顯示：`正在與 Supabase 同步旅行資料…`。

## 範圍與不變項目

### 納入範圍

- 手動登入成功後的首次同步。
- app 啟動時，偵測到既有 Supabase session 的自動登入同步。
- 同步中的全畫面阻擋、讀取失敗畫面、重新同步，以及同步成功後的畫面恢復。
- 避免 `onAuthStateChange` 與登入表單送出造成重複同步或過期回應覆寫較新的流程。
- 對應的無障礙、測試及 PWA 快取版本發布規則。

### 明確不做的事

- 不修改 Supabase schema、RLS、RPC、bucket、資料表欄位或任何既有雲端資料內容。
- 不改變既有「雲端有旅程時讀回資料；雲端尚無旅程時依既有流程上傳本機資料」的同步語意；後者也必須完成才算同步成功。
- 不改變登出流程、唯讀分享模式、旅程權限、資料合併規則或一般的「立即同步」按鈕語意。
- 不讓使用者在同步失敗時改用舊本機旅程；要使用 app 必須重新同步成功。

## 建議方案：全畫面同步閘門

在 app 根節點之外加入一個覆蓋整個視窗的同步閘門。它有 `loading`、`error`、`success` 三個具體狀態；`success` 是短暫的內部完成狀態，完成資料套用與畫面渲染後立即移除覆蓋層，不需額外停留動畫。

| 方案 | 優點 | 缺點 | 結論 |
| --- | --- | --- | --- |
| 全畫面同步閘門 | 不會洩漏舊快取；成功與失敗的規則清楚；可真正阻擋互動 | 需新增覆蓋層與狀態協調 | **採用** |
| 僅在雲端面板顯示載入文字 | 改動較少 | 使用者仍可瀏覽／編輯舊資料，風險未解除 | 不採用 |
| 先清空旅程頁再於原頁顯示 spinner | 不會直接看到舊卡片 | 空白畫面容易被誤解，仍須處理焦點與操作入口 | 不採用 |

## 狀態與畫面規格

| 狀態 | 何時進入 | 畫面與互動 | 離開條件 |
| --- | --- | --- | --- |
| `idle` | 未登入的一般模式、登出完成、唯讀分享模式 | 不顯示閘門；沿用既有 app 行為 | 偵測到目標使用者的登入同步需求 |
| `loading` | 非唯讀 app 啟動、手動登入認證成功，或啟動時取得既有 session；在開始讀取前即進入 | 顯示不透明的全畫面覆蓋層、不可關閉。文案為「正在與 Supabase 同步旅行資料…」。底下可有不含進度百分比的載入指示 | 無 session 的啟動檢查完成，或該次有效同步完成，或讀取／必要的既有首次上傳失敗 |
| `error` | 有效同步讀取失敗，或雲端沒有旅程時必要的既有首次上傳失敗 | 保持全畫面覆蓋層；顯示「無法完成 Supabase 同步」和可安全顯示的具體原因；只提供主要按鈕「重新同步」 | 使用者按「重新同步」且該次有效同步成功；按鈕期間回到 `loading` 並停用按鈕 |
| `success` | 有效同步已完成資料讀回／既有首次上傳，且資料、選取旅程與畫面恢復已完成 | 不向使用者停留顯示；先解除阻擋，再讓 app 可操作 | 立即回到 `idle` |

「原因」須保留可判斷性，例如網路中斷、權限拒絕或 Supabase 回傳的錯誤訊息；不可顯示密碼、access token、refresh token、完整 request payload 或其他敏感資料。未知錯誤顯示「發生未預期的連線錯誤，請檢查網路後重新同步。」

## 觸發與資料流

### 啟動時的既有 session

1. 唯讀分享模式直接略過雲端初始化與同步閘門，維持目前唯讀畫面。
2. 一般模式在第一次 render 前先開啟 `loading` 閘門，再建立 Supabase client、呼叫 `getSession()`；此短暫啟動檢查是避免 session 尚未判定時閃現舊本機資料的必要保護。
3. 若沒有 session，移除閘門並進入 `idle`，本機未登入模式照舊可使用。
4. 若有 session，設定目標使用者後保留既有的 `loading` 閘門，再排入該使用者的同步。不得先讓舊本機旅程可被瀏覽或點擊。
5. 只有有效同步完整套用資料並完成 render／恢復可用畫面後，才解除閘門。

### 手動登入

1. 表單驗證失敗或 Supabase 認證失敗時，維持既有登入表單與錯誤處理；尚未成功登入，不啟動同步閘門。
2. `signInWithPassword` 成功取得使用者後，立刻以該使用者建立同步請求並顯示 `loading` 閘門。
3. 同步完成前，登入表單、雲端面板、旅程列表與所有 app 控制項都不可操作。
4. 成功後清空密碼欄位、以同步完成後的資料恢復畫面。失敗則進入 `error`，不回露舊本機旅程。

### 單一同步協調器

實作新增一個唯一入口（名稱可為 `requestInitialCloudSync`），所有「首次登入／session 恢復」來源都只能呼叫它，不可直接各自呼叫 `loadCloudLibrary()`。

每次請求建立單調遞增的 `syncAttemptId`，並記錄 `targetUserId`；目前有效請求稱為「同步世代」。協調器規則如下：

1. 相同 `targetUserId` 的 `loading` 請求若仍在進行，回傳同一個 promise，不另開網路讀取。
2. `onAuthStateChange(SIGNED_IN)` 與登入表單送出若指向同一使用者，必須共用同一世代，因此只同步一次。
3. 新的使用者、登出、或新的重試會使舊世代失效；若可中止 HTTP 請求可中止，但即使無法中止，舊請求完成時也必須被忽略。
4. 每個 `await` 後、寫入 `state.library`、`localStorage`、選取旅程、錯誤訊息、render 或關閉閘門前，都要確認該世代仍是目前有效世代，且 `state.cloudUser.id === targetUserId`。
5. 不符合第 4 點的過期回應不得寫入資料、不得 render、不得改變閘門狀態，也不得顯示錯誤。
6. 同步成功才可清除本次錯誤並切至 `success`；同步失敗只讓目前世代切至 `error`。
7. 「重新同步」以目前已登入使用者建立新世代；若其間已登出或使用者改變，按鈕不得對舊使用者發出同步。

`onAuthStateChange` 仍負責更新認證狀態，但它不得和表單 submit 各自套用雲端資料。事件若是 `SIGNED_IN`，交由協調器去重；若是 `SIGNED_OUT`，使目前世代失效、移除閘門並保留既有登出行為。token 刷新等不代表帳號切換的事件不得重跑首次同步。

### 同步完成的原子性

同步資料處理沿用既有順序：取得雲端旅程、補齊協作資料、保留既有未發布私人待辦合併規則、決定有效的選取旅程與頁面狀態、寫回本機快取、render、恢復 view state。這一整段在同一有效世代內才可提交。

成功的定義是上述流程全部成功；不能在「已取得 trips 但協作資料尚未讀完」或「已寫入資料但尚未 render」時解除閘門。雲端沒有旅程時，既有的首次上傳也要成功才可解除閘門。任何一步失敗都不解除閘門。

## 無障礙與鍵盤規格

- 閘門使用 `role="dialog"`、`aria-modal="true"` 與清楚標題；`loading` 可用 `role="status"`、`aria-live="polite"` 宣告同步文案。
- `error` 的錯誤標題與原因使用 `aria-live="assertive"`，進入錯誤時把鍵盤焦點移到「重新同步」。
- 閘門存在期間，app 主內容設為 `inert`；若瀏覽器不支援，再加上 `aria-hidden="true"` 並以焦點管理確保 Tab 不會進入背後控制項。
- 載入中沒有可取得焦點的取消／關閉按鈕；錯誤時只有「重新同步」可作為下一步，且按鈕具有可見焦點樣式。
- 不只靠顏色或 spinner 傳遞狀態；文字必須完整表意，並遵守 `prefers-reduced-motion`，避免必要性以外的持續動畫。

## 登出與唯讀分享模式

- 唯讀分享模式 (`isReadonly`) 不初始化此閘門、不發出 Supabase session 同步、也不改變目前的唯讀畫面或可瀏覽資料。
- 使用者主動登出時，立即讓任何進行中的同步世代失效並依既有流程登出；不得把登出中的延遲讀取結果重新套入畫面。
- 登出本身不顯示同步閘門、不新增讀取或上傳，也不改變既有登出後的本機使用模式。

## 測試策略

### 單元測試

- 無 session：啟動檢查期間維持閘門；確認無 session 後移除閘門，且不呼叫雲端旅程讀取。
- 既有 session：在讀取前進入 `loading`；完整成功後才回到可用畫面。
- 手動登入成功：同步只由協調器啟動一次，即使同時收到相同使用者的 `SIGNED_IN` 事件。
- 同一使用者的重複請求共用 promise；不同使用者或重試建立新世代。
- 舊世代在新使用者登入、登出或重試後完成時，不能寫入 library／localStorage、不能 render，也不能改寫目前的錯誤或閘門。
- 讀取失敗、協作資料讀取失敗、與雲端空資料時的既有首次上傳失敗，都進入 `error` 且保留錯誤原因。
- 點「重新同步」後只有成功才解除閘門；失敗會回到新的 `error`。

### 介面與無障礙檢查

- 在 `loading` 與 `error` 截圖確認覆蓋層覆蓋完整視窗，背後舊旅程不可見或不可辨識，且不能點擊、捲動、Tab 進入或以快捷鍵操作。
- 確認載入文案完全等於「正在與 Supabase 同步旅行資料…」。
- 模擬網路或 Supabase 讀取錯誤，確認原因清楚、沒有敏感資訊，焦點落在「重新同步」，按下 Enter／Space 可重試。
- 測試登入、已存 session 重新整理、帳號 A 同步中切換帳號 B、同步中登出、及唯讀分享連結；逐一確認畫面不被舊回應覆寫。

### 回歸檢查

- 同步成功後，旅程、待辦、預訂、支出、協作成員與原本的 view state 依既有規則恢復。
- 雲端沒有旅程時，既有首次上傳流程仍可完成，之後才能使用 app。
- 登出、註冊、一般立即同步、離線本機未登入模式與唯讀分享模式維持原有行為。

## PWA 發布與快取版本

此功能會新增／修改 HTML、JavaScript 與 CSS，因此發布時必須同時完成下列版本更新：

1. `index.html` 中 app、CSS 及任何新增模組的查詢版本號一併遞增。
2. `sw.js` 的 cache 名稱遞增，且預快取清單中的 app、CSS、HTML 相關版本與 `index.html` 完全一致；若拆出同步閘門模組，也加入預快取並帶相同新版本。
3. 部署後以正式 GitHub Pages 重新載入，確認 Service Worker 已安裝新 cache，並在桌面與手機實測既有 session、手動登入、失敗重試三種畫面。

不使用 force push；先在功能分支完成測試與截圖檢查，再經驗證後合併至 `main`。

## 驗收條件

1. 手動登入與既有 session 自動登入都先顯示全畫面「正在與 Supabase 同步旅行資料…」，同步完成前無法操作或瀏覽任何舊本機旅程。
2. 同步成功後，才以同步完成後的資料與既有 view state 恢復 app。
3. 讀取或必要首次上傳失敗時，畫面保持阻擋，清楚顯示安全的原因及「重新同步」按鈕；成功前不得使用 app。
4. `onAuthStateChange` 和登入 submit 對同一登入只會共同使用一次同步；過期請求永遠不能覆寫較新的帳號、重試或登出流程。
5. 登出與唯讀分享模式行為不受影響。
6. Supabase schema、RLS 與資料內容均沒有為此功能而改變。
7. 閘門具備指定 aria、焦點管理、鍵盤操作與減少動畫支援。
8. 對應測試通過，且 app／CSS／Service Worker 快取版本同步更新。
